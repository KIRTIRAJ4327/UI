Part 1

Spec-driven development with Spec Kit

In spec-driven development the team writes down what to build and why before the AI agent writes code. The specification, plan and task list are Markdown files kept in the repository next to the code.

All Source. The developer runs each command in the coding agent's chat and reviews the result before the next one.

What it has beyond the basic flow

  • Two more processes. Bug fixing (assess, fix, test, with a verdict of verified, partial or failed) and idea assessment (ending in go, needs clarification, or kill). Source
  • Workflows. YAML definitions chain commands, shell tasks and human review gates into runs that can pause and resume. The bundled workflow puts a gate after the specification and after the plan. Source
  • Four ways to customise. Presets change templates and wording. Extensions add commands and hooks. Workflows automate. Bundles package a setup for a team or role. Source
  • Governed catalogs. An organisation can host a private catalog of approved add-ons. Microsoft's developer blog recommends giving it priority over the community catalog. Source Search
  • Model Context Protocol server. Experimental, local only, read-only: four tools that list artifacts and workflows. Source

Azure DevOps

The community bundle Spec Kit for Azure DevOps (spec-kit-ado, catalog version 0.3.2, repository at 0.4.0, last commit 12 November 2026) is the closest thing to our platform in the Spec Kit world. Source

  • The developer pulls a story from Azure Boards. The agent writes the spec, plan, code and tests.
  • Three approvals are built in: post questions to the story, create the Tasks, open the pull request. The agent shows the exact change and waits for a clear yes.
  • Each acceptance criterion is tied to a named test in a per-story checklist, which is attached to the story when it closes.
  • Optional sign-offs by a business owner, technical owner and QA. A person writes an approval comment on the story in Azure DevOps, and the comment includes a hash of the exact files signed. Who may sign is read from the target branch, so a feature branch cannot change it.
  • It ships Azure Pipelines templates for a gate, a branch guard and a strict verification step.
  • Limits it states itself: Azure Boards only (no Jira or GitHub Issues), a personal access token is required, and its checks are "guard rails for a team that reviews its pull requests, not a lock on a machine".

The Unified Product Delivery Platform

Our platform is a web console in which an AI agent takes a business change request through eight stages, and a named person approves each stage. Everything in this part describes the clickable prototype. It runs in the browser on demo data. No agent, pipeline, database or Azure service is connected. Prototype

Where Spec Kit is stronger

  • It exists, is free, and is released several times a week.
  • It works with almost any coding agent and tracker.
  • Multi-repo and Azure DevOps already run, through add-ons.
  • It can be shaped to a team's process without waiting for a vendor.

Where the platform design is stronger

  • People who never open a terminal can read, question and approve.
  • Who may approve what is enforced in one place, not per repository.
  • One audit record covers the change from request to rollback.
  • It covers the stages after the pull request, where a bank's controls sit.

Both panels Our view, drawn from the table above.

What to do

  • Stop positioning the platform against Spec Kit. The claims "no multi-repo", "no gates" and "stops at implementation" are out of date and a technical buyer will check them.
  • Position the platform as the governance layer above a spec-driven engine. The Developer Agent step could run Spec Kit in the repository, and the platform could hold the approvals, roles and audit record.
  • Pilot spec-kit-ado on one real story. It is the cheapest way to learn how far free tooling already goes for an Azure DevOps bank, and what is still missing for auditors and business approvers.
  • Fix the weaknesses we share. Add a fast path for low-risk changes and a bug-fix path, so the platform is not open to the same "too heavy" criticism.
  • Replace copy-and-paste with a real connection. Spec Kit's workflow runs, verdict inputs and experimental MCP server are the natural points to connect to.
  • Vet before use. Any community add-on needs a code review and a pinned version in a private catalog before it touches a bank's repositories.
